# Clip-distance compatibility

## Current CullDistance coverage (2026-10-11)

Drivers without native CullDistance but with geometry shaders expose the
compatibility feature. Device creation strips the virtual feature and enables
the native geometry stage without changing application-owned inputs. A generated
geometry shader discards an entire point, line or triangle when every vertex is
negative for the same cull plane. Mixed signs and zero distances are retained.
There is no CPU geometry or pixel readback in this implementation.

Static point list, line list/strip and triangle list/strip/fan pipelines with
plain vertex/fragment stages are supported. Adjacency, tessellation, application
geometry stages, dynamic topology and rasterizer-discard CullDistance pipelines
remain unsupported and fail pipeline creation rather than silently ignoring the
cull output. This is bounded application compatibility, not a Vulkan conformance
claim. Non-solid polygon emulation has its own complete filled-draw fallback;
that fallback does not justify ignoring CullDistance.

`build-cull.sh` checks generated SPIR-V and 24 immutable device-feature cases.
On x300, eight automatic insertion modes passed 576 pixel readbacks, with no
validation errors or live custom allocations: direct/member-decorated outputs,
points, lines, triangles and combined Clip/CullDistance. These used formally
built isolated layer SHA-256
`15c33e9b2365a74aa9c442606d2cd3a46a52429cdb4e1485d2055effe65ac11c`.
An APK containing the same formally built layer has also run Hell Clock on
x300 with empty Steam launch options: characters and scenery render correctly,
movement works, and shooting enemies advances the attack tutorial to the
interaction tutorial. This is limited gameplay evidence, not a full game or
cross-device regression. Redmi regression remains pending. Earlier sections
below record development history, not the current feature-exposure policy.

## Geometry-stage feasibility for culling and edge output (2026-10-11)

The `scaled-vertex-primitive-cull-validation` and
`scaled-vertex-primitive-lines-validation` modes (also with `-block`) reuse the scaled-input render
probe with generated native geometry stages. They enable only the driver's
reported geometryShader feature. The vertex fixture starts with a real
CullDistance built-in. The shared distance extractor converts it to a user
varying consumed by the geometry stage. The separate `-automatic` cull modes
submit the original vertex module and no application geometry stage, exercising
the compatibility layer's pipeline insertion. Neither shaderCullDistance nor
fillModeNonSolid is advertised yet.

Each mode checks twelve input formats and six distance configurations: inside,
all outside one plane, mixed signs with no common outside plane, all outside
the second plane, a second mixed case, and zero distances. Culling requires
all vertices to be negative for the same plane. Edge output checks colored
pixels, a bounded nonempty edge footprint and an empty interior. Both geometry
variants preserve positions from the vertex producer; the edge adapter never
substitutes a fixed triangle. It does not
establish Vulkan polygon-line coverage or back-face-culling equivalence.

On x300 both modes passed 24 pipeline cases and 72 image readbacks each,
with zero validation errors and no live custom allocations at shutdown.
Vertex fixtures and the GLSL reference geometry are generated by
`shaders/generate-primitive.py` and validated
as Vulkan 1.1 SPIR-V. The fixture declares Position-only built-in blocks on
both sides of the vertex/geometry interface; the initial implicit blocks
failed interface validation and are not acceptance evidence.

This establishes a GPU implementation route, not a game fix. General shader
interface translation, user geometry/tessellation stages, topology, face
culling, line/point rasterization and transform feedback remain to be designed
and verified before either core feature can be advertised.

The primitive adapter now builds geometry SPIR-V from the extracted vertex
outputs rather than using the fixed GLSL geometry fixture. It preserves output
types, locations and interpolation decorations, separately clones input
aggregate types and copies aggregate leaves. The initial whole-block copy
crashed this Mali compiler; sharing input/output aggregate types then produced
an empty image. Neither result is acceptance evidence. With separate types
and leaf copies, all four direct/block and triangle/edge modes pass on x300
(288 readbacks, zero validation errors, no live custom allocations).

Automatic insertion also passes the direct and block cull modes: 144 readbacks,
zero mismatches, zero validation errors and no live custom allocations. The
application does not enable geometryShader; device preparation enables the
native feature internally without modifying application inputs. Twelve host
checks cover absent features, legacy features and Features2 chains, including
prefix and suffix preservation. The formal layer used for these runs has SHA-256
`d1548c6e58bb2be7be030133b4d33494851920b8397eadf989ba5daaa40f908d`.
Its normal twelve-format scaled-input and 384-readback BC volume regressions
also pass with zero validation errors.

Automatic culling currently accepts static triangle list/strip/fan pipelines
with plain vertex/fragment stages. Other topologies, additional pre-raster
stages, dynamic topology and rasterizer discard are not implemented. General
core-feature exposure and game acceptance remain incomplete. These runs use
an isolated formally built library, not a newly installed APK.

The primitive adapter also accepts zero cull distances for edge output. The
`scaled-vertex-primitive-lines-validation-no-cull` probe uses an ordinary
Position/color vertex interface, with no cull declaration or synthetic cull
varying. It passes 72 image readbacks on x300. The two existing direct/block
edge modes also pass 144 readbacks, with zero mismatches, validation errors
and live custom allocations. This tests the GPU adapter directly; automatic
polygonMode translation and full face-culling/clipping semantics are still
unimplemented, so fillModeNonSolid must not be advertised.

An isolated native polygonMode LINE investigation does not justify changing
the advertised feature: requesting fillModeNonSolid from the x300 backend
returns VK_ERROR_FEATURE_NOT_PRESENT at device creation. A separate probe
without that request produced filled triangles, not edges; that deliberately
invalid Vulkan usage is diagnostic evidence only, not a supported path.

Distance planning reserves the full location span of matrices, arrays, wide
vectors and member-decorated interface blocks. Cull locations are replanned
after ClipDistance extraction to avoid overlapping the two injected varyings.
The host rewrite check covers the location spans. The automatic `-clip` and
`-clip-block` modes now cover combined clip/cull GPU output: an active clip
plane removes the left half of the image while the six cull configurations
either preserve the right half or discard the entire primitive.

This caught a module-creation error: active ClipDistance was translated only
at pipeline creation, after the placeholder shader had already reached the
driver with an unsupported capability. Module creation now translates it too,
while retaining the original interface for joint pipeline planning. The two
combined modes and two original automatic cull modes passed 288 readbacks on
x300, and the twelve-format scaled regression passed 36 more. All five modes
reported zero pixel mismatches, zero validation errors and zero live custom
allocations using formally built layer SHA-256
`873b8e208802712db946c8f208808180a32f11cb7c5b35466151f5e03e683382`.
These remain isolated-library tests, not APK or game acceptance.

Mali reports `shaderClipDistance=false`. Blender 4.3 `VKBackend::is_supported`
requires that bit. The ICD does the Vortek-shaped automatic path: advertise
the feature, strip it from `vkCreateDevice` before the HAL, and rewrite
used `ClipDistance` outputs to a user Location plus fragment `OpKill`.

No application environment variable. Emulation runs only when the physical
device lacks the feature. `HYBRIS_VULKAN_COMPAT_CLIP_DISTANCE=0` is not
required and is not a product switch.

Host rewrite check: `clip_rewrite_check.c` with `generate-clip.py`.
The mixed clip/cull fixture also verifies that translating ClipDistance keeps
an independently written CullDistance output and passes SPIR-V validation.
This preservation is not CullDistance emulation on drivers lacking that feature.
The same check extracts CullDistance from both independent variables and
gl_PerVertex members without removing active ClipDistance. Independent
variables retain their IDs and load/store uses rather than creating an
unwritten shadow output. On x300 the extracted independent form passes the
six primitive configurations above. The structure form also passes both GPU
modes: 72 readbacks per mode, zero mismatches, zero validation errors and zero
live custom allocations. The normal scaled-input regression remains unchanged
and passes all twelve formats.
Device diagnostic: probe mode `blender-vk` prints `BLENDER_VK_REQ` against
the Blender 4.3 minimum list.
Pipeline pNext (dynamic rendering) does not skip the rewrite; only extra
shader stages, stage pNext, or pipeline libraries do. Unused clip/cull
declarations are stripped before the HAL module is created. Fragment
rewrite reuses existing `OpTypeBool` and inserts the clip test after
function `OpVariable`s in the first block.


## Blender investigation, 2026-09-09

The X300 product had the current ICD but an older `libhybris-common.so.1`
(build-id `76a53de13ad0ee13083078669bb067da5d8b1965`). Its known-build Mali
MMUD hook still required an explicit switch. The same first-pipeline shader
pair compiled through the current isolated runtime, while the product
runtime crashed. Replacing only common with the current automatic-hook
build allowed that pipeline to compile without a compatibility switch.
Deploy the ICD and its common/linker dependencies as one coherent build.

The next crash was in the Mali shader compiler on Blender's third graphics
pipeline. The fragment rewrite split the entry block but left an existing
`OpPhi` incoming predecessor pointing at the original entry label. The
original shader passed `spirv-val`; the rewritten one failed its predecessor
check. The rewrite now retargets those predecessor operands to the final
clip continuation block, leaving value IDs unchanged. In the captured
third fragment, the only resulting binary difference is word 363:
predecessor ID 5 becomes ID 127. The corrected module passes validation.

Evidence is retained in the Arlinux parent workspace at
`build/mali-pipeline-investigation/20260909T101306/`:

- `phi-fix-build.log`: full AArch64 build and runtime manifest validation.
- `blender-phi-fix-dump-104151/`: 128 original/converted module pairs, all
  256 modules passing `spirv-val --target-env vulkan1.2`; JSON validator
  results, shader files, runtime manifest, loaded maps and device screenshot.
- `blender-phi-fix-104040/`: real Blender 4.3.2 reaches its Python timer,
  submits/presents and exits normally after the correction.

**Rendering acceptance remains failed.** The Blender content is black,
with Mali queue faults (and a tiler heap OOM in one run), despite successful
Vulkan return codes. Timer execution and a clean exit prove startup progress,
not a working UI. These runs use isolated libraries; they do not claim the
installed product libraries have been updated. No WSI changes were made as
part of this investigation.

Follow-up runs `blender-phi-fix-normal-104321` (without `--debug-gpu`) and
`blender-phi-fix-sync-104426` (SyncVal explicitly confirmed active, no shader
printf) still show GPU faults. The SyncVal run reports no VUID or
synchronization errors; this does not rule out errors introduced below the
layer by the ICD or driver. `blender-phi-fix-small-104546` uses an 800x600
window and additionally saves Blender's own GPU screenshot as `client.png`.
That screenshot shows only a partially drawn UI, while Android's screenshot
shows a gray client area. Queue faults and GPU timeouts persist, so the
failure is not limited to a large window or Android screenshot capture.


## Unused clip planning and later application evidence

The font vertex module declared ClipDistance without writing it. Module
creation removed this unused built-in, but pipeline planning still planned a
clip varying from the original declaration. The resulting fragment kill read
an unwritten location. Planning now first applies the same unused-built-in
cleanup. This is separate from the `OpPhi` predecessor correction above.

The existing six-distance shader rewrite check still passes. An audit of the
64 original vertex/fragment pairs from `blender-phi-fix-dump-104151` now yields
64 zero-distance plans and no planning errors; results are retained in
`clip-unused-plan-audit.json`. No new unit test was introduced. This audit
alone does not prove rendering correctness for shaders that use clip distances.

Further diagnosis found broken rendering suspension chains and missing host
flushes in Blender's texture/immediate uploads. Scoped handling now produces
the default scene, splash, text and toolbar, but repeated updates still report
Mali GPU timeouts. The old black-frame observations above remain historical
failures; current results and open acceptance limits are in
[Blender Vulkan compatibility](../../docs/blender-vulkan-compat.md).

## Initialized D3D9 outputs, 2026-10-18

Heaven 4.0 through Bionic Wine/DXVK failed pipeline creation with
`VK_ERROR_FEATURE_NOT_PRESENT` before reaching Mali. Its captured vertex shader
has initialized output variables. SPIR-V `OpVariable` accepts an optional
initializer, but the distance parser recognized only the four-word form;
location planning therefore rejected otherwise valid initialized outputs.
The parser now records both four- and five-word forms.

`generate-clip.py` adds a validated fixture with an initialized matrix output
occupying locations 16–19 and an array at 20–21. The existing rewrite check
requires the clip varying to start at 22. This fixture fails on the old parser
and passes on the correction; all previous clip/cull checks and rewritten
SPIR-V validation also pass. The real captured Heaven vertex shader plans six
distances at location 16 and its rewritten module passes Vulkan 1.1 validation.

Fresh X300 product-instance rendering evidence and the candidate runtime hash
are recorded in the parent ARLinux repository's
`docs/X300-WINLATOR-PERFORMANCE.md`. This change does not disable clipping,
change capability reporting, or substitute software rendering.
